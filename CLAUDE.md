# munasi — правила проекта

Генератор коротких вертикальных видео с боями персонажей (TikTok/Shorts, 1080x1920, 30fps).

## Архитектурные правила (не нарушать)

1. **`src/sim/` ничего не знает о рендере.** Только чистые функции и типы данных.
   Ноль импортов из `src/render/`, `src/export/`, ноль обращений к fs, canvas, ffmpeg.
2. **Вся случайность идёт через seeded RNG** (`src/sim/rng.ts`, mulberry32).
   `Math.random` запрещён во всём `src/`. Есть тест, который это проверяет.
3. **Одинаковый seed = побайтово одинаковое видео.** Никаких зависимостей от
   `Date.now()`, порядка обхода Map/Set с непредсказуемыми ключами, плавающих
   таймингов. Симуляция целиком детерминирована; рендер — чистая функция от снапшота.
4. **Каждый модуль покрыт тестами до того, как двигаемся дальше.**

## Почему бой устроен именно так

Три решения в `src/sim/simulate.ts`, которые выглядят как мелочи, но держат на
себе весь проект. Не «упрощать» их не разобравшись.

1. **`DAMAGE_VARIANCE = 0.35` и жирные криты в ростере.** Исход боя — это
   гонка двух чисел: побеждает тот, у кого больше произведение
   `dps × эффективное HP`. За матч происходит ~25 ударов, разброс усредняется,
   и при узкой дисперсии преимущество в 3% по статам превращается в 100%
   винрейта. Тогда невозможны ни баланс (35-65% недостижимы), ни драматургия
   (нет камбэков). Широкий разброс урона + `critChance` 0.22-0.38 при
   `critMult` 2.3-3.0 — это то, что делает исход по-настоящему неопределённым.
2. **Урон копится за тик и применяется, когда все отбили** (`applyPendingDamage`).
   Иначе тот, кого проверяют первым, бесплатно выигрывает все тики, где оба
   нанесли бы смертельный удар: систематические +3 п.п. стороне A.
3. **У каждой стороны свой поток RNG** (`deriveSeed(1)` / `deriveSeed(2)`).
   Один общий поток чередует броски бойцов, и корреляция соседних значений
   mulberry32 стоит стороне A измеримого преимущества. Проверено: с общим
   потоком одинаковые бойцы дают 52.8% / 47.2%, с раздельными — 49.0%.

## Баланс ростера

- Правило: ни одна пара не выходит за 35-65%. Проверка — `pnpm balance`
  (500 боёв на пару, 66 пар, ~30 секунд).
- **Выборка в 200 боёв даёт ±3.5 п.п. шума** — этого хватает, чтобы пометить
  красным честную пару. Поэтому CLI по умолчанию гоняет 500. Не «чинь» пару,
  которая вылезла на 34% при 200 боях: сначала перемерь.
- Числа в `fighters.json` **не пишутся руками** — они выводятся из
  `roster.ts` скриптом `pnpm calibrate`. Правишь дизайн в `roster.ts`,
  прогоняешь калибровку, проверяешь балансом.
- Калибровка держит равным `dps × эффективное HP`, а не время до смерти:
  равное время до смерти означает мощность ∝ HP², и самый толстый боец
  выносит всех.
- Аое — естественный контрпик к призыву: он бьёт по миньонам. Поэтому HP
  миньона задаётся явным блоком `minion` и не масштабируется вместе с уроном —
  миньон должен переживать одно попадание аое.

## Что уже измерено (не перепроверять с нуля)

`pnpm diagnose` считает это заново; результаты на текущем ростере:

- **Отбор сида окупается.** Лучший из 500 сидов даёт +25..30% drama score
  к медиане на всех проверенных парах. Порог «меньше 15% — отбор бесполезен»
  не достигнут, отбор оставляем.
- **Перекоса стороны A нет.** 10 000 боёв одинаковыми бойцами: 49.91%
  при 95% ДИ [48.94%, 50.89%]. Ничьих 9.8% — у зеркальных бойцов совпадает
  расписание ударов, так что взаимное добивание в одном тике не редкость;
  оно даёт **ничью** (`applyPendingDamage`, затем общая проверка обеих сторон),
  а не победу фиксированной стороны. Драматургия штрафует ничью в 0.2x,
  поэтому в ролик такой бой не попадёт.
- **Rubber-banding проверен и отклонён.** Прототип живёт за флагами
  (`MatchRules`, по умолчанию выключено) — `pnpm diagnose --comeback`:

  | вариант | drama | длина | разброс винрейтов |
  | --- | --- | --- | --- |
  | baseline | 66.3 | 26.8s | 33-66% |
  | rubber only | 66.1 | 22.4s | 28-68% |
  | waves only | 66.8 | 22.9s | 14-84% |
  | both | 64.9 | 19.9s | 15-85% |

  Ни один вариант не поднял drama (лучшее +0.5 — в пределах шума), зато все
  укорачивают бой: когда оба бьют сильнее по мере потери HP, гонка
  заканчивается быстрее и длина уходит к нижней границе окна 22-38с.
  Волны миньонов вдобавок ломают баланс. **Криты обратно не сужаем** —
  условие «та же драма при более узкой дисперсии» не выполнено.

## Гонтлет — основной формат

Один работяга против трёх начальников по очереди. Структура снята с референса
(`refs/README.md`): двое на экране, указатель идёт по составу, HP челленджера
переносится между раундами и не восстанавливается, у каждого члена команды
полное HP на старте своего раунда.

- Команды собираются из поля `faction` в `roster.ts`, не списком руками:
  6 работяг × 20 троек начальников = 120 матчапов.
- Обе стороны носят своё HP из ростера (1000-1400). Перевес челленджера — в
  уроне: `GAUNTLET_TUNING` в `teams.ts` (`tempo` задаёт длину раунда,
  `challengerPower` — долю прохождений). Решает `pnpm calibrate:gauntlet --solve`.
- Замерено на 500 прогонах **под `GAUNTLET_RULES`**: прохождений 59.4%, до
  третьего раунда доходит 99.6%, средняя длина 29.9с, таймаутов 0%.
- **Осторожно с калибратором.** `sampleGauntlets` берёт правила аргументом, и
  CLI долго вызывал его без них: мерил гонтлет с дисперсией 1v1, без пикапов и
  без `openingCooldown`. Отсюда числа 50.5% и 49.4% в прежних отчётах — это
  конфигурация, которая не отгружается. Сейчас CLI печатает обе строки.
  Разложение (500 прогонов на строку):

  | конфигурация | прохождений | длина |
  | --- | --- | --- |
  | дисперсия .35, без разгона (то, что мерили) | 49.4% | 32.7с |
  | дисперсия .15, без разгона | 51.4% | 32.7с |
  | дисперсия .15, разгон .22 | 53.6% | 30.7с |
  | + пикапы = отгружается | 59.4% | 29.9с |

  Основной сдвиг дают **пикапы (+5.8 п.п.)**: хилка ценнее для той стороны,
  которая тащит HP через раунды, а начальник каждый раунд выходит полным.
  `openingCooldown` тоже не бесплатен: +2.2 п.п., а не ноль, как я написал.
  Цель 50% сейчас не выполняется — это решение по балансу, не косметика.
- **Дисперсия урона в гонтлете уже (±15%), чем в 1v1 (±35%)** — и это не
  противоречие. В 1v1 без широкого разброса преимущество в 3% даёт 100%
  винрейта. Гонтлет делает близкий финал структурно: к третьему раунду
  челленджер уже потрёпан, и везение для напряжения не нужно.
  Замер: drama 88.1 при ±35% против 88.7 при ±15%.
- После смерти раунд держит кадр 26 кадров (`ROUND_HOLD_FRAMES`), иначе
  анимация смерти (24 кадра) не успевает проиграться и боец стоит целым на 0 HP.
  Держать меньше — соблазн, но недоигранная смерть хуже короткой паузы, темп
  берётся из `openingCooldown`, а не отсюда.

## Движение — третий гейт, и самый важный

Геометрия и темп вместе всё ещё пропускают слайд-шоу: кадр скомпонован верно,
события идут, а картинка стоит. `src/export/motion.ts` меряет это на **готовом
mp4**, потому что зритель получает именно его.

Метод: декодируем окно 6 секунд из середины в оттенки серого 270x480, считаем
долю пикселей, изменившихся сильнее чем на 8/255 (ниже — шум кодека).

| | референс | было | стало |
| --- | --- | --- | --- |
| изменившихся пикселей за кадр | 12.7% | 3.0-4.9% | 9.0% |
| кадров с изменением <1% | 0% | 8.9-26.8% | 0.0% |

Порог гейта: **≥8% на кадр и <5% статичных кадров**.

Причина провала была одна: у бойцов не было позиций. Симуляция была гонкой двух
чисел, рендер ставил фигуры в фиксированные слоты. Починено в трёх местах:

1. **`src/sim/movement.ts` — позиции в симуляции.** У каждого бойца (x, y) в
   единичном квадрате арены, x вбок, y от дальнего края к ближнему. Цикл:
   сблизился, ударил, отошёл, сместился вбок. Треугольная волна на дистанции —
   у неё нет ветки «стоит», и тест держит правило «не дольше 10 кадров на
   месте» (удержание кадра после смерти не считается, там играет анимация).
   **Позиция не решает урон.** Расписание атак по-прежнему только по кулдауну,
   движение подстроено под него. Иначе исход боя зависел бы от того, успел ли
   боец дойти, и калиброванный ростер перестал бы быть калиброванным.
   Свои потоки RNG (`deriveSeed(4)`/`(5)`), чтобы не сдвинуть существующие.
2. **`attackRate: 3` в `GAUNTLET_RULES`.** Втрое чаще, втрое слабее удар. DPS
   не меняется по построению. Цена измерена: прохождений 59.4% -> 61.6%, потому
   что при втрое большем числе ударов разброс усредняется и фаворит выигрывает
   чаще. Дисперсию поднимать бесполезно — проверено, 0.15/0.22/0.26/0.30 дают
   61.4-62.4%, разницы нет.
3. **`src/render/gauntletCamera.ts` — камера следит.** Пан за серединой между
   бойцами с запаздыванием, зум под их разлёт. Трек считается один раз на бой и
   кэшируется в `WeakMap`: `gauntletFrameLayout` обязана остаться чистой
   функцией от `(result, frame)`, а lerp — состояние.

**Зум запаздывает только внутрь.** Приближение можно тянуть, отдаление — нет:
пока камера догоняет, боец успевает пересечь стену арены. На отдалении зум
ставится жёстко на «влезает точно».

### Размер и движение конкурируют за одни и те же 924px

Это стоит помнить, прежде чем крутить константы. Первая версия солвера
резервировала максимальный разлёт пары внутри арены — бойцы получились **9%
высоты кадра**. Сейчас база считается по **медианному** разлёту, а крайние
случаи добирает зум (0.86-1.12). Итог: 22.1-40.5% по ходу боя.

Из-за этого же снят гейт «bbox двух бойцов не пересекаются»: при живых позициях
пара сходится и расходится, и на сближении силуэты обязаны пересекаться —
именно так это и выглядит в референсе. Держит их читаемыми разнос по глубине:
ближний крупнее и рисуется поверх, плюс контур 4px.

## Темп — второй гейт

Геометрия не равна движению: кадр может пройти всю композиционную проверку и
при этом стоять на месте. `src/sim/tempo.ts` меряет вторую половину, тест
`tempo.test.ts` держит правило: **ни одного промежутка без событий длиннее
1.2 секунды** (36 кадров).

Замер до правки показал, где именно мёртвый воздух: **все превышения сидели на
стыках раундов, ни одного внутри раунда**. Стык — это 27 кадров удержания
смерти плюс 20-33 кадра до первого удара новичка, до 2.00с. Внутри раунда
худший промежуток и тогда был 33 кадра, то есть уже в норме.

Чинилось сжатием паузы, а не эффектами: `openingCooldown: 0.22` в
`GAUNTLET_RULES` укорачивает **первый** кулдаун атаки в каждом раунде. Обе
стороны получают одинаковую фору. Цена замерена честно: +2.2 п.п. к
прохождениям (51.4% -> 53.6%) и -2.0с к длине. Не ноль.
По умолчанию множитель 1, поэтому **1v1 не тронут вообще** (умножение на 1
побитово тождественно, `Math.round` там сознательно не используется).

Стало: стыки 0.80-0.93с, худший промежуток по выборке 1.07с, тихих кадров
10-29% вместо 16-31%.

### Длина: 26-28 секунд не окупаются

Проверено, ничего не менялось. Сдвиг `tempo` в `GAUNTLET_TUNING` укорачивает
ролик, но платит драмой и балансом:

| tempo | прохождений | длина (сырая / отобранная) | drama сырая | drama отобранная |
| --- | --- | --- | --- | --- |
| 1.03 (текущий) | 61.7% | 29.0с / 29.4с | 88.5 | 99.8 |
| 1.12 | 59.2% | 26.9с / 28.4с | 87.9 | 99.9 |
| 1.20 | 56.1% | 25.3с / 27.5с | 86.8 | 99.7 |
| 1.28 | 55.3% | 23.8с / 26.7с | 85.3 | 99.2 |
| 1.36 | 54.0% | 22.6с / 25.9с | 83.6 | 98.7 |

Целиться в 26-28с — это tempo 1.12-1.20: сырая drama падает на 0.6-1.7,
прохождения уходят к 56%. Отобранная drama почти не двигается, потому что
отбор из 200 сидов вытягивает и худший вариант. Вывод: выигрыш по длине
маленький, а сырое качество распределения падает. Оставлено как есть.

## Хук: первые две секунды

- **Кадр 0 — это превью в ленте**, и он проверяется тестом как статичная
  картинка: имя челленджера ≥ 2.2% высоты кадра, имена всех троих начальников
  ≥ 1.9%, панель состава не пересекает имя, оба бойца целиком в арене на полном
  HP. Имя раньше делило полосу с панелью, ужималось до 35px (1.8%) и в ленте не
  читалось — теперь три блока стоят стопкой и имя занимает всю ширину.
- **Холодное открытие включено по умолчанию**, выключается `--no-cold-open`.
  30 кадров сильнейшего всплеска урона **из последнего раунда**
  (`findGauntletColdOpen`), затем склейка на реальное начало.
- Жёстко и под тестом: окно не содержит добивающего удара и не заходит в
  последние 20% ролика. Спойлер финала стоит дороже слабого открытия.

## Финальная карточка

Главное число ролика — **сколько у победителя осталось HP**. «Прошёл всех на
8 HP» и есть вся драма гонтлета, поэтому оно вынесено отдельной строкой, а
виджет победителя обведён рамкой.

Что было и почему это плохо: затемнение всего кадра до трети яркости (победителя
не видно), имя без подгонки кегля (уезжало за оба края кадра), два виджета,
которые оба читались как ноль, и две секунды статики в конце.

Стало: карточка ушла **под арену**, в полосу, где стоит «РАУНД 3/3» — она уже
пустая и уже под текст. Арену не перекрывает вообще (это в гейте), победитель
виден целиком. Имя ужимается по ширине, держится 34 кадра (1.13с).

Промежуточный вариант — плашка внутри арены, прижатая к её полу — закрывал
победителя от груди вниз, то есть ровно то, ради чего его в кадре и оставляли.

## Композиция кадра — гейт, а не вкусовщина

`src/render/gauntletLayout.ts` считает все прямоугольники до отрисовки,
`layout.test.ts` прогоняет по ним каждый кадр видео. Правила:

- ни один прямоугольник HUD не пересекается с другим; HUD неподвижен
- bbox бойца целиком внутри кадра
- высота бойца: цель 30% высоты кадра, жёсткий пол 22%
- **bbox двух бойцов не пересекаются** — кроме 14 пар, которым иначе не хватает
  ширины арены на пол 22%; гейт печатает их поимённо
- **дальний боец меньше ближнего и стоит выше** во всех кадрах
- числа урона не пересекаются с виджетами HP
- **все всплывающие числа, включая криты, целиком внутри арены**
- **арена в каждом кадре совпадает с константой** — защита от того, что
  её снова начнут решать
- **два бойца одного раунда различаются по средней светлоте ≥ 60 из 255**
- **контраст цифры HP к своей подложке ≥ 4.5:1** на 25/50/75% — меряется по
  отрисованным пикселям, не по константам палитры
- **текст финальной карточки целиком внутри арены**, и виджет победителя
  ненулевой, если он победил
- бойцы стоят на линии земли арены

До появления гейта видео из 977 кадров валило все 977: бойцы были 13.5% и
15.7% высоты, ноги висели на 71%, 58 кадров резали бойца краем.

**Гарантия строгая: стену арены не пересекает ничего.** Ни тело, ни мусор от
смерти. Не край кадра — кадр 1080 шириной, арена 924, и старая гарантия по
кадру спокойно пускала разлёт смерти сквозь стену того самого квадрата, внутри
которого идёт бой.

### Арена прибита, двигается камера

`ARENA` в `gauntletTheme.ts` — константы: квадрат со стороной 92% ширины кадра,
отцентрован по горизонтали, верх на 29.5% высоты, рамка 3.2% ширины. Ни одно из
этих чисел не выводится из бойцов.

Единственное, что меняется от кадра к кадру, — камера (`layout.camera`): пан и
зум в мировых координатах арены. Раньше арена подгонялась под пару, то есть
единственный элемент, который обязан стоять на месте, ездил вместе с бойцами.

### Две линии земли, а не одна

Пара разнесена по глубине, как в референсе. **Ближний — всегда начальник**
(константа по стороне, не по матчапу): стоит на линии 0.90 внутренней высоты
арены, рисуется в 1.12 раза крупнее и поверх. Челленджер — дальний: линия 0.70,
меньше. Одна общая линия оставляла верхнюю треть квадрата пустой в каждом кадре.

**Ширина — вот что связывает, а не линия земли.** Это стоит запомнить, потому
что интуиция говорит обратное. Боец в 30% высоты кадра имеет ширину 430-590px;
двое таких плюс зазор — 860-1180px, а внутренняя арена 924px. Замер при нулевом
перекрытии: цель 30% недостижима для **32 пар из 36**, худшей не хватает 677px
из 902. Даже пол 22% без перекрытия не держат **14 пар из 36** (худшей не
хватает 260px).

Поэтому перекрытие оставлено, но только как аварийный клапан: пара сходится
ровно на недостающее и ни на пиксель больше. 22 пары из 36 стоят полностью
раздельно, гейт печатает список остальных. Итог по ростеру: дальний 22.2-30.3%,
ближний 23.6-38.7%, в среднем 27.1%. Пол 22% держится везде.

Размер решается так: цель 30% для того из двоих, кто ниже на экране (не для
ближнего — он крупнее на 12% по построению, и якорь на нём топил дальнего под
пол), затем потолки по крыше и полу арены и по ширине. Крыша считается по
**габариту движения, а не по росту в покое**: idle-качание и отдача поднимают
макушку выше стойки — гейт это поймал, бойцы вылезали за верх арены на 7px.

Пара центруется **по телам, а не по габаритам смерти**: центровка по разлёту
сдвигала пару вбок весь бой из-за двух секунд умирания.

### Читаемость: контур и светлота

- **Контур 4px** тёмным вокруг каждого бойца (`FIGHTER_OUTLINE`). Это то, что
  даёт референсу читаемость, и оно решает сразу две беды: боец не сливается с
  синим фоном и не сливается со вторым бойцом там, где они перекрываются.
  Контур — четыре штампа альфы фигуры со сдвигом вверх/вниз/влево/вправо.
  Кольцо из двенадцати штампов красивее на диагоналях, но стоит 685 мс на кадр
  против 61 мс у четырёх; при 30 fps разницу не видно, а рендер в шесть раз
  дольше видно сразу.
- **Работяги светлые, начальники тёмные.** Правило структурное, не попарное:
  работяги 174-212, начальники 73-99, худшая пара 74.8 при пороге 60.
  До правки палитр не проходили 22 пары из 36 (пекарь против арбитра — 3.4).
  Если пара не проходит — это ошибка ростера, гейт печатает список.
- **Цифра HP всегда светлая на постоянной тёмной подложке.** Раньше цвет цифры
  переключался по заполнению виджета — это работает, только если фон под
  цифрой однородный, а он не однородный: граница заливки проходит через
  перекладину примерно на половине HP, и цифра оказывалась наполовину на белом,
  наполовину на сером. Контраст сейчас 15:1 при пороге 4.5:1.
- **У каждого бойца есть отдача от попадания** (`Pose.hurt`): отбрасывание
  назад плюс сплющивание, применяется рендером, а не артом бойца — иначе те, у
  кого idle нарочно статичный, весь бой выглядят картинкой. Одной белой вспышки
  не хватало: грузчик читался как неподвижный спрайт.
- Крит передаётся **кеглем и цветом**, не дальностью: 10% ширины кадра против
  5.5% у обычного удара, `#ffe45c` против белого. Подъём числа короткий (2.2%
  высоты) и клампится в полосу между виджетами HP и полом арены — раньше крит
  улетал вверх и оказывался за ареной, в зоне HUD.
- **В замахе нет наклона, есть шаг вперёд** (`Transform.lunge`). Наклон плюс
  подъём читались как падение, а не как удар. «Вперёд» — это ось экрана, и она
  разная в форматах: гонтлет ставит пару бок о бок (`lungeAxis: "x"`), дуэль
  ставит друг над другом (`"y"`), поэтому шаг хранится отдельно от `dx`/`dy`.

## Технические решения

- Тик симуляции: **60/сек**. Видео: **30 fps**. Снапшот пишется каждый второй тик,
  ровно по одному на кадр видео.
- События (`MatchEvent`) несут номер **кадра видео**, не тика — рендер и звук
  работают в кадрах.
- Таймаут боя: 60 секунд (3600 тиков / 1800 кадров).
- Числа с плавающей точкой в симуляции: копятся только в аккумуляторах
  (`attackCooldown`, `hp`). Все сравнения — через `<= 0`, без epsilon-трюков.
- Формат `MatchResult` сериализуется в JSON без потерь — на этом построен тест
  детерминизма.
- **У каждого бойца своя функция отрисовки** в `src/render/fighters/<id>.ts`:
  свой силуэт, свой предмет-подпись, своя idle-анимация, свой замах и своя
  смерть. `spriteId` бойца равен его `id`. Никаких сторонних изображений и
  реальных людей — всё рисуется кодом.
  `src/render/sprites.ts` остался запасным вариантом (архетип по хешу
  `mage:265`) для бойцов вне ростера: фикстуры, разовые конфиги.
- **Силуэты защищены тестом** `silhouette.test.ts`: попарный IoU масок,
  порог 0.70. Порог выведен из замеров, а не назначен: у отгруженного ростера
  худшая пара 0.663, а две реально сливавшиеся пары давали 0.739 и 0.713.
  Если тест упал — перерисовывай силуэт, а не поднимай порог.
- **Порядок кадров задаётся планом** (`src/render/framePlan.ts`), а не
  равенством «кадр видео = кадр симуляции». На этом держится холодное
  открытие, и это же читают воркеры рендера и звуковая шина.
- Звук синтезируется кодом в `assets/audio/` при первом экспорте; свои файлы
  можно положить туда же под теми же именами — существующие не перезаписываются.
- Шрифт DejaVu лежит в `assets/fonts/` и регистрируется явно: метрики текста
  входят в байты кадра, и полагаться на системный fontconfig нельзя, если
  нужен одинаковый результат на разных машинах.

## Стек

TypeScript strict + Node 20+ + pnpm, vitest, `@napi-rs/canvas` для кадров,
ffmpeg через `child_process` для сборки. Внешних зависимостей минимум.

## Структура

```
src/sim/      — чистая симуляция боя (rng, types, simulate, drama, coldOpen)
src/render/   — отрисовка кадров в PNG
src/render/fighters/ — по файлу на бойца: силуэт и анимации
src/export/   — сборка видео через ffmpeg
src/content/  — JSON-конфиги персонажей, баланс, матчапы
src/cli/      — точки входа
assets/       — спрайты, звуки
out/          — готовые видео (в .gitignore)
```

## Команды

```
pnpm test        # vitest
pnpm typecheck   # tsc --noEmit
pnpm calibrate   # пересчитать fighters.json из roster.ts
pnpm balance     # матрица винрейтов по всем парам (500 боёв на пару)
pnpm matchups    # пары по возрастанию дисбаланса
pnpm diagnose    # распределение drama, перекос стороны A (+ --comeback)
pnpm calibrate:gauntlet          # баланс гонтлета (--solve, --variance)
pnpm frame       # отрендерить один тестовый кадр
pnpm generate --count 20
```
